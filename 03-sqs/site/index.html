TOPIC 03

Amazon SQS
— コンポーネントを疎結合にするメッセージキュー

マイクロサービス・分散システム・サーバーレスアプリケーションを疎結合化してスケールさせる、 フルマネージドなメッセージキューイングサービスについて学んだメモ。

Standard / FIFO キュー 可視性タイムアウト デッドレターキュー Lambda連携

SQS は何をしてくれるのか

システム間を直接の同期呼び出しで繋ぐと、受信側がダウンしていると送信側も止まってしまう、受信側の処理速度が 生成速度に追いつかないとリクエストが失われる、受信側のスケール機構を自前で作り込む必要がある、といった 問題が起きやすい。SQS をコンポーネント間に挟むことで、送信側(プロデューサー)と受信側 (コンシューマー)を疎結合にし、それぞれを独立してスケール・デプロイできるようにする。

メッセージの消失や他サービスの可用性を気にすることなく、任意のボリュームでメッセージを送信・保存・受信でき、 メッセージ指向ミドルウェアの運用にまつわる複雑さをAWSが肩代わりしてくれる。

プロデューサーが送信したメッセージをキューが保持し、コンシューマーやLambdaがポーリング/イベントで 受信する。処理に規定回数失敗したメッセージはデッドレターキューへ移動する。

キューの種類: Standard と FIFO

高スループット優先

Standard キュー

ほぼ無制限のスループットを持ち、メッセージは少なくとも1回配信(まれに重複あり)。 順序保証はベストエフォート。重複や順序の入れ替わりを許容できる高スループット処理向け — 例: メディアのアップロードとリサイズ処理の分離、クレジットカード検証タスクの複数ワーカーへの割り当て。

順序・重複排除優先

FIFO キュー

デフォルトで最大3,000msg/秒(バッチ利用時、高スループットモードで最大70,000msg/秒まで拡張可)。 メッセージは正確に1回処理され、送信順=受信順を厳密に保証する。操作順序が重要、 または重複が許されない処理向け — 例: ユーザー入力コマンドの順序実行、価格変更の正しい順序での反映。

主要な概念

  • 可視性タイムアウト受信したメッセージは一定時間(デフォルト30秒、最大12時間)他のコンシューマーから不可視になる。処理完了前に削除しないと再配信される。
  • デッドレターキュー(DLQ)指定回数(maxReceiveCount)処理に失敗したメッセージを隔離する別キュー。不良メッセージが他メッセージをブロックするのを防ぐ。
  • ロング/ショートポーリングショートポーリングは一部サーバーに即座に問い合わせ、ロングポーリングは最大1〜20秒待って空応答を減らす。ほぼ常にロングポーリングが推奨。
  • 遅延キュー(Delay Queues)投入時から最大15分メッセージを不可視にできる。可視性タイムアウトが「受信時」に不可視化するのに対し、こちらは「投入時」。
  • サーバーサイド暗号化(SSE)メッセージ本文をKMSキーで暗号化して保存する。キュー名やメッセージIDなどのメタデータは対象外。
  • Lambda連携Event Source MappingでSQSをLambdaのイベントソースとして登録し、バッチ単位で自動的にポーリング・呼び出しできる。

メッセージのライフサイクル

  1. 送信(SendMessage)
    プロデューサーがメッセージをキューに送信する。遅延キューが設定されていれば、指定秒数は不可視のまま。
  2. 受信(ReceiveMessage)
    コンシューマーが受信すると、可視性タイムアウトの間そのメッセージは他のコンシューマーから見えなくなる。
  3. 処理 & 削除(DeleteMessage)
    タイムアウト内に処理を終えて削除すれば完了。時間が足りない場合は ChangeMessageVisibility で延長できる(最大12時間まで)。
  4. 再配信 or デッドレターキューへ
    削除されないまま可視性タイムアウトが過ぎると再びキューに戻り、別のコンシューマーに配信される。 maxReceiveCount を超えて失敗し続けたメッセージは DLQ に移動し、redrive で元のキューへ 再投入したり調査したりできる。

Lambda との統合(Event Source Mapping)

SQSキューをLambdaのイベントソースとして登録すると、Lambdaサービス側が最大1,000並列(リージョンあたり)の ポーリングスレッドを立ち上げてキューを監視し、メッセージのバッチで関数を同期呼び出しする。関数が正常終了 するとバッチ内のメッセージが削除され、エラーやタイムアウトの場合は可視性タイムアウト経過後にメッセージが キューへ戻る。

実行ロールには AWSLambdaSQSQueueExecutionRole が必要。バッチサイズはStandardキューで 最大10,000件、FIFOキューで最大10件。Lambdaの関数タイムアウトは、キューの可視性タイムアウトより 短く設定する必要がある(目安として可視性タイムアウトを関数タイムアウトの6倍以上にする)。 

# CLIでイベントソースマッピングを作成する例
aws lambda create-event-source-mapping --function-name ProcessSQSRecord --batch-size 10 \
  --event-source-arn arn:aws:sqs:us-east-1:111122223333:my-queue

料金

従量課金制で、最低利用料金なし。全リクエストが課金対象だが、無料枠がある。

  • 無料枠: すべてのアカウントで月100万リクエストまで無料
  • SendMessage / ReceiveMessage / DeleteMessage などすべてのリクエストが同一料金で課金される
  • ロングポーリングを使わずに高頻度でポーリングし続けると、メッセージが返らない「空の受信」もリクエストとしてカウントされ、想定以上の課金につながりやすい
  • SSEを使う場合はKMSのAPI呼び出し分の料金が別途発生する

ハンズオン手順

いずれも AWS CLI で完結する。リージョンは --region または aws configure の デフォルトリージョンに従う。

1. Standard / FIFO キューの挙動差を確認する

代表的なケース: 注文イベントのように「発生順どおりに処理したい/重複を避けたい」要件があるかどうかで キュー種別を選ぶ判断を、実際の送受信結果で確認する。

aws sqs create-queue --queue-name standard-demo-queue
aws sqs create-queue --queue-name fifo-demo-queue.fifo \
  --attributes FifoQueue=true,ContentBasedDeduplication=true
  1. Standard キューに ABC を続けて送信し、receive-message の結果が送信順どおりとは限らないことを確認する。
  2. 同じ内容を再送し、複数回 receive-message すると重複して受信されうることを確認する。
  3. FIFO キューには --message-group-id を付けて同じ3件を送信し、常に送信順どおりに 受信できることを確認する。
  4. FIFO キューに同一本文を再送し、ContentBasedDeduplication(5分間の重複排除ウィンドウ) により重複配信されないことを確認する。
  5. 確認後は両キューを delete-queue で削除する。

2. 可視性タイムアウトと再配信を観察する

代表的なケース: ワーカーの処理が長引き、可視性タイムアウト内に DeleteMessage できなかった 場合の再配信挙動を検証する。

  1. 可視性タイムアウトを10秒にしたキューを作成し、メッセージを1件送信する。
  2. receive-message で受信するが、delete-message は呼ばない。
  3. 15秒待ってから再度 receive-message し、同じメッセージが再び返ってくることを確認する。
  4. ApproximateReceiveCount 属性で受信回数が増えていることを確認する。
  5. 今度は change-message-visibility で延長してから処理を完了させ、delete-message で削除して再配信されないことを確認する。

3. DLQ への隔離と redrive を試す

代表的なケース: 特定のメッセージだけが処理に失敗し続け、キュー内の他メッセージをブロックする状況を 再現し、DLQ による隔離と redrive による復旧を確認する。

  1. DLQ を作成し、その QueueArn を控える。
  2. メインキューを作成し、RedrivePolicy で DLQ と maxReceiveCount=3 を設定する。
  3. メッセージを1件送信し、receive-message するが削除せず可視性タイムアウトが切れるのを 待つ、を3回繰り返して失敗をシミュレートする。
  4. 4回目にはメインキューではなく DLQ 側にメッセージが移動していることを確認する。
  5. start-message-move-task で DLQ から元のキューへ redrive し、メインキューに メッセージが戻ることを確認する(進捗は list-message-move-tasks で確認)。

4. SQS を Lambda のイベントソースとして登録する

代表的なケース: S3 アップロードなど非同期に発生するイベントを SQS 経由で受け取り、Lambda が バッチ処理する構成(サムネイル生成やデータ加工など)を模したハンズオン。

  1. AWSLambdaSQSQueueExecutionRole をアタッチした Lambda 実行ロールを作成する。
  2. 受信メッセージをログ出力するだけのシンプルな Lambda 関数(タイムアウト短め、例: 10秒)を作成する。
  3. 可視性タイムアウトを関数タイムアウトの6倍以上(例: 60秒)にしたキューを作成する。
  4. create-event-source-mapping でバッチサイズを指定して紐付ける。
  5. 複数メッセージを送信し、CloudWatch Logs でバッチ単位に呼び出されることを確認する。
  6. 特定メッセージでわざと例外を投げさせ、ReportBatchItemFailures(部分バッチ失敗レポート) の設定有無で再試行対象の範囲が変わることを比較する。

5. CDK / Terraform で IaC 化する

代表的なケース: 手順1〜4で手動確認した「メインキュー + DLQ + Lambda イベントソースマッピング」を 再現可能な形でコード化する。

  1. 03-sqs/cdk/(または terraform/)を作成し、CDK なら cdk init app --language typescript で初期化する。
  2. DLQ・メインキュー(deadLetterQueue / redrive_policy で紐付け、 可視性タイムアウトは Lambda タイムアウトの6倍以上)・Lambda 関数・イベントソースマッピングを定義する。
  3. cdk synth / terraform plan で意図した設定になっているか確認する。
  4. cdk deploy / terraform apply し、手順1〜4と同じ動作確認を行う。
  5. 確認後は必ず cdk destroy / terraform destroy で破棄する。

理解度クイズ

選択肢をクリックすると、正解と解説が表示されます。

Q1. Standard キューと FIFO キューの違いとして正しいものはどれか?

Standard キューはほぼ無制限のスループットを持つ代わりに「少なくとも1回配信」でまれに重複や順序の入れ替わりが起きる。FIFO キューはデフォルト最大3,000msg/秒(高スループットモードで最大70,000msg/秒)に抑える代わりに、メッセージを正確に1回処理し送信順=受信順を厳密に保証する。

Q2. 可視性タイムアウトの説明として正しいものはどれか?

可視性タイムアウトは、コンシューマーが受信したメッセージをデフォルト30秒(最大12時間)の間、他のコンシューマーから見えなくする仕組み。タイムアウト内に DeleteMessage しないと、メッセージは再びキューに戻り別のコンシューマーへ再配信される。

Q3. デッドレターキュー(DLQ)の役割として正しいものはどれか?

DLQ は、指定回数(maxReceiveCount)処理に失敗したメッセージを隔離する別キュー。不良メッセージがメインキューに残り続けて他メッセージの処理をブロックするのを防ぎ、後から start-message-move-task で redrive して調査・再投入できる。

Q4. SQS と Lambda の統合(Event Source Mapping)について正しいものはどれか?

実行ロールには AWSLambdaSQSQueueExecutionRole が必要。バッチサイズはStandardキューで最大10,000件、FIFOキューで最大10件。関数タイムアウトは可視性タイムアウトより短く設定し、目安として可視性タイムアウトを関数タイムアウトの6倍以上にすることが推奨される。

Q5. SQS の料金体系として正しいものはどれか?

無料枠は全アカウントで月100万リクエストまで。SendMessage/ReceiveMessage/DeleteMessageなどすべてのリクエストが同一料金で課金され、ロングポーリングを使わず高頻度にポーリングすると「空の受信」もリクエストとしてカウントされコストが増えやすい。SSEを使う場合はKMSのAPI呼び出し分の料金が別途発生する。
