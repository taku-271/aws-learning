TOPIC 04

Amazon Bedrock AgentCore Identity
— エージェントのための認証・認可基盤

AIエージェントという「非人間アイデンティティ」向けに、エージェントの身元管理・呼び出し元の検証 (インバウンド認証)・外部サービスへの認証情報の払い出し(アウトバウンド認証)を一元的に扱う サービスについて学んだメモ。

ワークロードアイデンティティ インバウンド認証(JWT/IAM) アウトバウンド認証(OAuth/APIキー) トークンボルト

AgentCore Identity は何をしてくれるのか

エージェントは「人間ではないが、人間に代わって(または自律的に)外部リソースにアクセスする」存在で、 従来のIAMユーザー/ロールだけでは表現しづらい認可パターンが発生する。複数の外部サービス(Slack、 GitHub、Google、Salesforceなど)ごとに異なる認証方式を自前で実装・保管するのはリスクが高く、 マルチテナント環境では「Agent AがUser 1の代わりにアクセスする際、誤ってUser 2のデータを取得して しまう」ようなクロステナント漏えいも防がなければならない。

AgentCore Identity はこれらを、SigV4・標準化されたOAuth 2.0フロー・APIキーを横断する形で 一元的に扱う。Amazon Bedrock AgentCoreの他コンポーネント(Runtime、Gateway)と統合されており、 それらを使う場合はインバウンド認証・アウトバウンド認証の多くを自動的に肩代わりしてくれる。

インバウンド認証で確立された「検証済みユーザー身元」が、そのままワークロードアクセストークンを 経由してアウトバウンド認証(トークンボルトのスコープ)に引き継がれる。

AgentCore Identity の主要コンポーネント

コンポーネント役割
Agent identity directory
(ワークロードアイデンティティディレクトリ)		エージェント/ワークロードのアイデンティティを作成・管理・整理する統一ディレクトリ。ARNで一意に識別され、AWSホスト・自己ホスト・ハイブリッドを問わず組織内エージェントの単一の真実源となる
Agent authorizer
(インバウンド認証)		エージェントを呼び出そうとしているユーザー/サービスが許可されているかを検証する
Resource credential provider
(アウトバウンド認証の設定)		エージェントが外部リソースサーバー(Google、GitHubなど)へアクセスするための認証情報を取得する設定を保持する
Resource token vault
(トークンボルト)		ユーザーのOAuthアクセス/リフレッシュトークン・APIキー・OAuthクライアントシークレットをAWS KMSで暗号化して保管し、エージェントが安全に取得できるようにする

インバウンド認証(誰がエージェントを呼び出せるか)

「誰がこのエージェント/Gatewayを呼び出せるか」を検証する仕組みで、AgentCore Runtime・Gateway 両方に共通の設定(CustomJWTAuthorizerConfiguration)で構成する。1つのRuntime/Gateway (バージョン)は同時に1つの認証方式のみをサポートする。

サービス間呼び出し

AWS IAM(SigV4)

AWS内のサービス間呼び出し向け。AWS認証情報でリクエストに署名する。IAM側の設定だけで完結し、 AgentCore Identity固有の追加設定は不要。

エンドユーザー認証

OAuth 2.0(JWTベアラートークン)

エンドユーザーが既存のIdP(Amazon Cognito、Okta、Microsoft Entra IDなど)を通じて直接認証する 場合。トークンの署名・発行者・有効期限を暗号学的に検証する。

JWTオーソライザーの設定項目

設定項目内容
Discovery URLIdPのOIDC Discoveryエンドポイント。指定するだけで、そのOIDC IdPが発行したトークンを動的に検証できる(事前オンボーディング不要)
Allowed audiencesJWTのaudクレームと照合する許可オーディエンス。トークンの使い回しを防ぐ
Allowed clientsJWTのclient_idクレームと照合する許可クライアントID
Allowed scopes許可するOAuthスコープ。設定した場合、少なくとも1つが一致する必要がある
Required custom claims特定クレーム(例: department)の値が期待値と一致することを要求するルール
  1. ①ユーザーがIdPで認証
    Cognito/Okta/Entra IDなどでエンドユーザーが認証し、ベアラートークン(JWT)を受け取る。
  2. ②クライアントがトークンを付与
    AuthorizationヘッダーにJWTを載せてRuntime/Gatewayを呼び出す。
  3. ③AgentCore IdentityがJWTを検証
    署名・有効期限・発行者(iss)を暗号学的に検証し、Audience/Client/Scope/カスタムクレームと突き合わせる。
  4. ④検証結果に応じて処理
    成功すればリクエストを処理、失敗すればエージェントコード実行前に拒否する。

ワークロードアイデンティティとワークロードアクセストークン

Runtimeにデプロイされた各エージェントには、自動的に一意のワークロードアイデンティティ が割り当てられる。これはエージェントのAWS環境内での「デジタルな身元」で、IAMロール・OAuth 2.0 トークン・APIキーのいずれを使う場合でも一貫した身元を保つ土台になる。

ワークロードアクセストークンは、エージェントがAgentCore Identityなどファースト パーティのAgentCoreサービスにアクセスするための、AWS署名付きのopaque(不透明)なトークンで、 外部サービスには直接使えない。Runtime/Gatewayが自動的に発行してエージェント実行環境に渡す。

パターンAPI内容推奨用途
JWTベースGetWorkloadAccessTokenForJWTエンドユーザーのJWT(発行者・署名・有効期限を暗号学的に検証)を渡してトークンを取得本番環境(推奨)
UserIdベースGetWorkloadAccessTokenForUserId文字列のユーザーIDをそのまま渡してトークンを取得。プラットフォームはこの文字列を検証しない開発/クイックスタート、または上流で身元解決済みの場合に限定

UserIdベースAPIのセキュリティ推奨事項

  • 信頼できるコンテキストから導出IAM呼び出し元IDやセッション属性からuserIdを導出し、クライアントから任意の値をそのまま受け取らない。
  • IAM権限を限定GetWorkloadAccessTokenForUserIdの権限を必要な範囲だけに絞り、ワイルドカードでの広範な付与を避ける。
  • 不要な経路をDeny常にJWTが使えるワークロードでは、UserIdベースの経路を明示的にDenyする。
  • IdPごとにuserIdを分割provider_id+user_idの形でパーティション分割し、IdP間のユーザーID衝突を防ぐ。
  • 監査ログを取得CloudTrailで呼び出しを監視し、想定外のuserId値を検知する。

アウトバウンド認証(エージェントが外部サービスへアクセスするしくみ)

外部サービスごとに Resource Credential Provider(OAuth2CredentialProvider またはApiKeyCredentialProvider)を作成し、クライアントID/シークレットや認可・トークン エンドポイントを登録する。Slack・GitHub・Google・Microsoft・Okta・Auth0・Cognitoなど主要ベンダーの 組み込み設定と、任意のOAuth 2.0プロバイダー向けのカスタム設定の両方に対応する。

3LO / Authorization Code Grant

ユーザー委任(user-delegated)

ユーザー本人の代わりに、そのユーザーが同意した権限範囲でリソースへアクセスする。初回は認可URLへの リダイレクトとユーザーの同意画面が必要(auth_flow="USER_FEDERATION")。

2LO / Client Credentials Grant

自律的(autonomous / M2M)

ユーザーを介さず、サービスレベルの認証情報でエージェント自身がアクセスする (auth_flow="M2M")。認可URLの提示やユーザーリダイレクトは発生しない。

初回アクセス時のフロー(ユーザー委任・3LO)

ユーザーがまだそのエージェントにアクセスを許可しておらず、トークンボルトに有効なトークンが 存在しない場合の流れ。

  1. ワークロードアクセストークンを取得
    エージェントがGetWorkloadAccessTokenForUserId(またはForJWT)を呼び出す。
  2. OAuthトークンをリクエスト
    GetResourceOauth2Tokenを呼び出し、ワークロードアクセストークン・Provider名・必要なスコープ・コールバックURLを渡す。
  3. 認可URLの発行
    有効なトークンがないため、AgentCore IdentityがsessionUriと認可URLを生成して返す。
  4. ユーザーへ同意を依頼
    エージェントが認可URLをユーザーに提示し、外部サービスの同意画面で許可してもらう。
  5. 認可コードの交換
    認可サーバーが認可コードをAgentCore Identityに送り、sessionUri付きでコールバックURL(セッションバインディング用)にユーザーをリダイレクトする。
  6. トークンをボルトに保存
    セッションバインディングで正しいユーザー・Providerの組み合わせを確定し、アクセストークン(とリフレッシュトークン)をトークンボルトに保存する。
  7. 以降はキャッシュを再利用
    同じユーザーからの呼び出しでは、キャッシュ済みトークンを使い再度の同意を求めない。期限切れ時はリフレッシュトークンで自動更新する。
セッションバインディング: CreateOauth2CredentialProviderを呼び出すと、 AgentCore Identityはそのプロバイダー専用の一意なOAuth2コールバックURLを発行する。このURLにより、 認可コード交換をクロスプロバイダーのリプレイ攻撃やCSRF類似の攻撃から守る。

トークンのスコープ分離

ワークロードアクセストークンは「エージェントのワークロードアイデンティティ + ユーザーID」を バインディングキーとしてトークンをキャッシュする。この暗号学的な紐付けにより、User 1の トークンがUser 2のリクエスト処理中に誤って使われる、といったクロステナントの漏えいを アプリケーションロジックのバグに関わらず防止する。

Q1. AgentCore Identity の4つの主要コンポーネントに含まれないものはどれか?

AgentCore Identityの主要コンポーネントは、Agent identity directory、Agent authorizer、Resource credential provider、Resource token vaultの4つ。Lambdaのコード署名機能はAgentCore Identityの構成要素ではない。

Q2. インバウンド認証のJWTオーソライザー設定で、「トークンが別のAPI向けに発行されたものを誤って使い回されることを防ぐ」ために使う項目はどれか?

Allowed audiences はJWTのaudクレームと照合する許可オーディエンスのリストで、トークンが意図した以外のAPIで使い回されることを防ぐ。Discovery URLはIdPの検証エンドポイント、Allowed scopesは許可する権限範囲、Required custom claimsは任意クレームの一致条件を扱う。

Q3. ワークロードアクセストークンの取得について正しいものはどれか?

GetWorkloadAccessTokenForJWTはJWTを暗号学的に検証してユーザーを一意に識別するため本番推奨。GetWorkloadAccessTokenForUserIdは文字列を検証せず扱う。ワークロードアクセストークンはファーストパーティのAgentCoreサービス専用で外部サービスには使えず、Runtime/Gateway管理のアイデンティティはトークンを直接取得できないよう制限されている。

Q4. アウトバウンド認証の「ユーザー委任(3LO)」と「自律的(2LO/M2M)」の違いとして正しいものはどれか?

3LO(USER_FEDERATION)はユーザー本人の同意を得るAuthorization Code Grantで、初回は認可URLへのリダイレクトが発生する。2LO/M2M(M2M)はサービスレベルの認証情報でエージェントが自律的にアクセスするClient Credentials Grantで、ユーザーリダイレクトは発生しない。どちらのトークンもトークンボルトで管理される。

Q5. セッションバインディングとトークンのスコープ分離について正しいものはどれか?

CreateOauth2CredentialProviderはProviderごとに一意なコールバックURLを発行し、認可コード交換をそのProvider専用に限定する(セッションバインディング)。また、ワークロードアクセストークンは「ワークロードアイデンティティ+ユーザーID」をバインディングキーとしてキャッシュされるため、User 1のトークンがUser 2の処理に誤用されることを防ぐ。
