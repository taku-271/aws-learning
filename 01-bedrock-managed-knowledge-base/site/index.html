TOPIC 01

Amazon Bedrock Managed Knowledge Base

ベクトルDBの構築・運用を自分でしなくてよい、完全マネージド型のRAG（Retrieval-Augmented Generation）サービスについて学んだメモ。

2026年6月 GA

Bedrock Knowledge Bases とは

Amazon Bedrock Knowledge Bases は、生成AIアプリケーションに RAG を実装するための Bedrock の機能。データの場所を指定するだけで、Bedrock がドキュメントの取得・チャンク分割・ 埋め込みベクトル化・ベクトルストアへの保存/同期までを内部で行う。カスタムのデータ統合や データ同期の実装は不要で、マルチターン会話のためのセッションコンテキスト管理も組み込み。

Bedrock Agent に接続すると、エージェントがユーザー入力に応じて適切な Knowledge Base を 自動選択し、取得情報をプロンプトに追加してくれる。取得結果には出典（citation）が付くため、 ハルシネーション抑制とファクトチェックのしやすさにつながる。

データの取り込み・チャンク分割・埋め込み・ベクトルストアをBedrockが内部で完結させ、 アプリ/エージェントは Retrieve系APIを呼ぶだけで検索結果や出典付きの回答を得られる。

2種類の Knowledge Base

現在、性質の異なる2つの作成方法がある。「Managed Knowledge Base」は Bedrock Knowledge Bases 全体の別名ではなく、2026年6月にGAした特定の作成モードを指す点に注意。

新 · 2026年6月GA

Managed Knowledge Base

ベクトルストアの選定・構築・スケーリングをBedrockが完全に肩代わりする。利用者はデータソースを 指定するだけで、チャンク分割からベクトル化・保存までがブラックボックス化される。

従来 · 2023年11月GA

Knowledge base with vector store

OpenSearch Serverless / Aurora / Pinecone などのベクトルストアを自分で用意する(Quick create も可)。チャンク戦略・埋め込みモデル・再ランカーを個別に選んで細かく制御できる。

Managed Knowledge Base（新） Knowledge base with vector store（従来）
GA時期 2026年6月 2023年11月

データソース S3, SharePoint, Confluence, Google Drive, OneDrive, Web Crawler（ネイティブ6種） S3, Confluence, Salesforce, SharePoint, Web Crawler など

Managed Knowledge Base の特徴

  • インフラ管理不要ベクトルDB・データパイプライン・検索基盤の運用が不要。埋め込みモデルも Default にすれば自動選択・自動管理。
  • ネイティブコネクタ6種Amazon S3, SharePoint, Confluence, Google Drive, OneDrive, Web Crawler。自動データ同期に対応。
  • ハイブリッド検索キーワード検索とセマンティック検索を組み合わせ。
  • ドキュメントランキング検索結果を re-ranking して精度を向上。
  • agentic retrieval複雑なマルチホップクエリに対し、クエリプランニング・中間応答の評価・再ランキングを自動オーケストレーション。
  • マルチモーダル対応テキストに加え動画・音声・画像を横断した Knowledge Base を構築可能。
  • AgentCore とのネイティブ統合権限の自動生成やオブザーバビリティが組み込みでエージェントに接続できる。
  • 対応リージョンUS East (N. Virginia), US West (Oregon), Asia Pacific (Sydney, Tokyo), Europe (Dublin, Frankfurt, London), AWS GovCloud (US-West)

クエリ用API

Knowledge Base（Managed / vector store 型 いずれも共通）へは以下の2つのAPIで問い合わせる。

  • RetrieveAndGenerate — クエリを埋め込みに変換 → Knowledge Base を検索 → 検索結果をコンテキストとしてプロンプトに追加 → LLMが生成した回答を返す、という一連の流れをまとめて実行。会話の短期記憶（セッションコンテキスト）も管理する。
  • Retrieve — 検索結果（関連チャンク）のみを返す。生成は行わず、後続の独自ワークフロー（関連度評価、別の回答生成ロジックなど）に使う。 LangChain の AmazonKnowledgeBasesRetriever などから利用できる。

Managed Knowledge Base の作り方（コンソール手順の概要）

  1. Bedrock コンソール → Knowledge bases → Create → Managed Knowledge Base
  2. Knowledge Base 名・説明を入力
  3. Embeddings model を選択（Default embedding model を選ぶと Bedrock が自動選択・管理）
  4. データソースを接続（まずは S3 が試しやすい）
  5. 作成後、データソースに対して ingestion job を実行してコンテンツを検索可能にする

CloudFormation/CDK では AWS::Bedrock::KnowledgeBase リソースの KnowledgeBaseConfiguration に ManagedKnowledgeBaseConfiguration（Managed型）か VectorKnowledgeBaseConfiguration（vector store型）のどちらかを指定する形になっている。

コスト比較（S3 Vectors / OpenSearch Serverless / Aurora Serverless との比較）

vector store 型 Knowledge Base で使える代表的なベクトルストアと、Managed Knowledge Base の料金体系を比べてみた。

Managed Knowledge Base の料金体系

ストレージ課金 + API呼び出し課金のシンプルなモデル。マルチモーダルパース・埋め込み・ 再ランキングはすべて込み（カスタムモデルに差し替えた場合のみ通常のBedrockモデル料金が 別途発生）。

項目単価
インデックスストレージ$5.00 / GB / 月
標準 Retrieve$1.00 / 1,000件
Agentic Retrieve$4.00 / 1,000件（+ 内部で発生する Retrieve 呼び出し分も別途 $1.00/1,000件で加算）
マルチモーダルパース・埋め込み・リランカー無料込み

AWS公式の試算例（SharePointから50GBを取り込み、月10万クエリのケース）： 標準Retrieveのみでストレージ$250+Retrieve$100=月$350、 Agentic Retrieve（平均2回の内部呼び出し）だとストレージ$250+Agentic$400+内部Retrieve$200=月$850。

自前のベクトルストアを使う場合（vector store 型 Knowledge Base）

「埋め込みモデルのトークン課金」+「ベクトルストア自体の課金」の二重構造になる。

ベクトルストア料金モデル特徴的なコスト構造
OpenSearch Serverless OCU時間課金、$0.24/OCU時間 最初のコレクションは indexing/search 合わせて最低4 OCUが常時課金。4 OCU×24h×30日=月$691.20が「待機しているだけ」でかかる最低ライン。ストレージは別途GB月課金。
Aurora Serverless（pgvector） ACU時間課金（目安 $0.12/ACU時間） 最小0 ACUまでオートポーズ可能→アイドル時はコンピュート課金ゼロにできる。ストレージは概ね$0.10/GB程度。
S3 Vectors ストレージ $0.06/GB + PUT/QUERYのリクエスト課金 プロビジョニング不要のサーバーレス。特化型ベクトルDB比で最大90%のコスト削減を謳う。低頻度アクセス・アーカイブ向け。

ポイント: OpenSearch Serverless は「動いていなくても」月$700弱かかる最低ラインがあるため、 小規模な学習用途やトラフィックが少ないアプリでは Managed KB の方が安くなるケースが多い。 一方、Aurora ServerlessやS3 VectorsはアイドルコストがOpenSearchより低く抑えられる。

パフォーマンス比較

ベクトルストアレイテンシ目安得意な領域
OpenSearch Serverless sub-10ms（高スループット・低レイテンシ） 高頻度クエリ、リアルタイム性が必要なアプリ、全文検索+ベクトル検索の併用
Aurora（pgvector） 数ミリ秒〜1桁ms（直接クエリ） リレーショナルDBとベクトル検索を同居させたい場合
S3 Vectors コールドで1秒未満、ウォームで約100ms 数十億ベクトル規模の低頻度アクセス・長期保存（RAGでも「たまにしか検索されない」用途向き）
Managed Knowledge Base 非公開（内部ストレージ層はAWSが最適化・非開示） ハイブリッド検索・ドキュメントランキング・agentic retrieval が標準搭載。同等機能を自前構築するとかなりの追加実装が必要

使い分けの指針

  • とにかく早く・安く始めたい / 小〜中規模データ / 運用コストをかけたくない — Managed KB（$5/GB + 従量課金、待機コストなし）
  • 超高スループット・sub-10msのレイテンシが必須 — OpenSearch Serverless（ただし待機コスト月$700弱は覚悟）
  • リレーショナルクエリとベクトル検索を同じDBでやりたい、トラフィックが波がある — Aurora Serverless + pgvector（オートポーズでコスト圧縮可）
  • 数十億ベクトル規模を激安で長期保存、検索頻度は低くてよい — S3 Vectors（ストレージ最安、レイテンシは妥協）

ハンズオン手順

1. S3データソースのManaged Knowledge Baseを構築し、Retrieve系APIで問い合わせる

代表的なケース: 社内FAQなどのドキュメント群をS3に置き、RAGチャットボットのバックエンドとして Managed Knowledge Base を試す。

  1. S3バケットを作成し、サンプルドキュメント(FAQのtxt/PDFなど数件)をアップロードする。
  2. Bedrockコンソールで Managed Knowledge Base を作成する(Embeddings model は Default の ままにして自動管理に任せる)。
  3. データソースとして手順1のS3バケットを接続する。
  4. ingestion job を実行し、コンテンツを検索可能にする。
  5. コンソールのテストチャットで質問を投げ、出典(citation)付きの回答が返ることを確認する。
  6. CLIから RetrieveAndGenerate / Retrieve を呼び出し、生成された 回答と関連チャンクそれぞれの結果を見比べる。
  7. 確認後、Knowledge Base と S3バケットを削除する。
aws bedrock-agent-runtime retrieve-and-generate \
  --input '{"text":"FAQの内容について教えて"}' \
  --retrieve-and-generate-configuration '{
    "type": "KNOWLEDGE_BASE",
    "knowledgeBaseConfiguration": {
      "knowledgeBaseId": "<KNOWLEDGE_BASE_ID>",
      "modelArn": "arn:aws:bedrock:us-east-1::foundation-model/anthropic.claude-3-5-sonnet-20241022-v2:0"
    }
  }'

aws bedrock-agent-runtime retrieve \
  --knowledge-base-id <KNOWLEDGE_BASE_ID> \
  --retrieval-query '{"text":"FAQの内容について教えて"}'

2. 既存のvector store型Knowledge Baseとコスト・構築の手間を比較する

代表的なケース: 同じデータセットに対して Managed Knowledge Base と、OpenSearch Serverless を自前構築する vector store 型 Knowledge Base の両方を作り、構築の手間と コストを比較する。

  1. 手順1と同じS3データソースを用意する。
  2. 手順1の要領で Managed Knowledge Base を構築し、必要だった設定項目数・構築時間を メモする。
  3. 「Quick create a new vector store」でOpenSearch Serverlessコレクションを自動構築する vector store 型 Knowledge Base を作成する。チャンク戦略・埋め込みモデルを個別に選択する 必要がある点を記録する。
  4. 同じ質問セットを両方に RetrieveAndGenerate で投げ、回答内容・レイテンシの 体感差を比較する。
  5. Billing/Cost Explorerで、OpenSearch Serverless側は待機中も最低ライン(4 OCU分)の 課金が発生する一方、Managed KBはストレージ+API呼び出し分のみで済むことを確認する。
  6. 確認後、両方のKnowledge Base、OpenSearch Serverlessコレクション、S3バケットを削除する。

理解度クイズ

選択肢をクリックすると、正解と解説が表示されます。

Q1. Managed Knowledge Base の最大の特徴として正しいものはどれか?

Managed Knowledge Base は、チャンク分割・埋め込みベクトル化・ベクトルストアへの保存/同期までをBedrockが内部で行う作成モード。データソースはS3のほかSharePoint、Confluence、Google Drive、OneDrive、Web Crawlerのネイティブ6種に対応し、埋め込みモデルもDefaultを選べばBedrockが自動選択・管理する。

Q2. Retrieve API と RetrieveAndGenerate API の違いとして正しいものはどれか?

RetrieveAndGenerate は、クエリの埋め込み変換・検索・プロンプトへの追加・LLMによる回答生成までを一連の流れとして実行し、会話のセッションコンテキストも管理する。一方 Retrieve は検索結果(関連チャンク)のみを返し、生成は行わない。後続の独自ワークフローに使いたい場合に向く。

Q3. OpenSearch Serverless と Managed Knowledge Base のコスト比較として正しいものはどれか?

OpenSearch Serverless は最初のコレクションでindexing/search合わせて最低4 OCUが常時課金され、4 OCU×24h×30日で月$691.20が「待機しているだけ」でもかかる下限になる。一方 Managed Knowledge Base はストレージ課金+API呼び出し課金のシンプルなモデルで、そのような待機コストの下限を持たない。

Q4. Managed Knowledge Base の機能について正しい説明はどれか?

Managed Knowledge Base はネイティブコネクタ6種(S3, SharePoint, Confluence, Google Drive, OneDrive, Web Crawler)に対応し、ハイブリッド検索・ドキュメントランキング・agentic retrieval が標準搭載。埋め込みモデルもDefaultを選べば自動選択・管理され、テキストに加え動画・音声・画像を横断したマルチモーダルなKnowledge Baseも構築できる。

Q5. パフォーマンス比較の観点で正しい組み合わせはどれか?

ベクトルストアごとに得意な領域が異なる。OpenSearch Serverless は sub-10ms の高スループット・低レイテンシが強みだが待機コストが高い。S3 Vectors はコールドで1秒未満・ウォームで約100msとやや遅いが、数十億ベクトル規模の低頻度アクセス・長期保存に向く。Managed Knowledge Base の内部レイテンシは非公開(AWSが最適化)。
