TOPIC 02

Amazon Bedrock AgentCore Gateway
— エージェント専用のセキュアな入口

AIエージェントがツール・他のエージェント・LLMへアクセスするための、単一のセキュアなエントリポイントを フルマネージドで提供するサービスについて学んだメモ。

MCP互換ツール変換 インバウンド/アウトバウンド認証 サーバーレス

Gateway は何をしてくれるのか

エージェントに独自ツールを持たせようとすると、社内APIやLambdaをMCPサーバーとして自前でラップする実装、 インフラの構築・スケーリング、ツールごとに異なる認証方式の管理、エージェント自身の認証検証など、 本質的でない作業が積み上がる。AgentCore Gateway はこれらを肩代わりし、開発者がエージェント 固有のロジックに集中できるようにする。

単なる「MCPツールゲートウェイ」に留まらず、既存のAPI・Lambda・他のエージェント(A2A通信)・複数モデル プロバイダーへのルーティングまでを扱う、エージェント向けAIゲートウェイとして位置づけられている。 Bedrock AgentCoreは Gateway 以外にも Runtime・Memory・Identity・Observability から構成されるが、 本トピックでは Gateway に絞る。

Gateway が単一の入口となり、Targetを介して既存API・Lambda・他エージェント・モデルプロバイダーを MCPツールとして束ねる。

主なメリット

  • ツール開発の簡素化既存のAPI/Lambdaを数行でエージェント対応ツールに変換できる。
  • 統一アクセスAPI・Lambda・他エージェント・モデルプロバイダーを1つのセキュアなエンドポイントに集約。
  • セマンティック検索でスケールツール数が増えてもx_amz_bedrock_agentcore_searchで自然言語から適切なツールを発見。
  • 包括的な認証インバウンド(エージェントの身元確認)とアウトバウンド(ツール接続)を1サービスで管理。OAuthフロー・トークンリフレッシュにも対応。
  • フレームワーク互換CrewAI、LangGraph、LlamaIndex、Strands Agentsなど主要OSSに対応。
  • サーバーレスインフラ管理不要、需要に応じ自動スケール、監査機能を内蔵。

コアコンセプト：Gateway と Target

Gateway はエージェントがアクセスする単一のMCPエンドポイント(URL)。ここに複数の Target を登録し、Targetを追加するとその裏側のAPI/Lambda/サービスがMCPツールとして Gateway経由で公開される。

Target種別内容
Lambda targetsAWS Lambda関数をMCPツールに変換する
OpenAPI targetsOpenAPI仕様(REST API)をMCPツールとして公開する
Smithy targetsSmithyモデル定義から型安全なMCPツールを構築する
MCP server targets既存の外部MCPサーバー(URLエンドポイント)にそのまま接続する
API Gateway stage targetsAmazon API Gatewayのステージをターゲットにする
HTTP runtime targets任意のHTTPランタイムをターゲットにする
Connector targetsBedrock Managed Knowledge Bases、Web Search Toolなどの組み込みコネクタ

インバウンド認証とアウトバウンド認証

Ingress ← エージェントを検証

インバウンド認証

Gatewayを呼び出すエージェント/クライアントを検証する仕組み。JWTベースの認証 (CUSTOM_JWT)が中心で、OIDCのDiscovery URL・許可するAudience/Client ID/Scope・ カスタムクレームの一致条件などを設定する。Amazon Cognitoをアイデンティティプロバイダーとして 使う構成がクイックスタートとして用意されており、agentcore createコマンドで 自動セットアップできる。

Egress → Targetへ接続

アウトバウンド認証

Gatewayが各Targetの裏側(Lambda実行ロール、外部APIのAPIキー、OAuthなど)へアクセスする際の 認証情報。Targetごとに異なる認証方式(IAMロール、APIキー、OAuth)を設定でき、Gatewayが 認証情報の交換・注入を代行する。

Runtime/Gateway双方で共通の仕組みとして、エージェントごとにワークロードアイデンティティ (AgentCore Identity)が割り当てられる。IAMロール、OAuth 2.0トークン、APIキーなど複数の認証手段を 横断して、エージェントの一貫した身元を保つ。

セットアップの基本フロー

  1. Gatewayを作成する
    インバウンド認証としてJWTオーソライザーを設定する。CognitoユーザープールをCLIで自動作成することも可能。
  2. 1つ以上のTargetを追加する
    Lambda、OpenAPI、MCPサーバーなど。Targetごとにツールスキーマとアウトバウンド認証情報を定義する。
  3. エージェントから接続する
    Strands Agentsなどのフレームワークからアクセストークンを取得してGatewayのMCPエンドポイントに接続し、 ツールを一覧・呼び出しする。

CLIでの例(Lambda Target)

# Gateway作成(対話式でCognito等をセットアップ)
agentcore create

# Lambda関数をTargetとして追加
agentcore add gateway-target \
  --name MyLambdaTarget \
  --type lambda-function-arn \
  --lambda-arn arn:aws:lambda:us-east-1:123456789012:function:MyFunction \
  --tool-schema-file tools.json \
  --gateway MyGateway

agentcore deploy

tools.json には、MCPツールとして公開する関数のスキーマ(name/description/inputSchema)を JSON Schemaで記述する。

Python SDK(GatewayClient)での例

from bedrock_agentcore_starter_toolkit.operations.gateway.client import GatewayClient

client = GatewayClient(region_name="us-east-1")

lambda_target = client.create_mcp_gateway_target(
    gateway=gateway,
    name=None,          # 省略すると自動生成
    target_type="lambda",
    target_payload=None, # 省略すると新規Lambdaが自動作成される
    credentials=None,    # 省略すると認証情報も自動作成される
)

料金

消費ベース(コンサンプションベース)の課金モデル。前払い不要・最低利用料金なし。

  • ListTools / InvokeTool / Search API などのAPI呼び出し回数に対して課金
  • セマンティック検索用にインデックスされたTarget数に対して課金
  • ネットワークデータ転送は標準のEC2料金が適用される
  • 顧客のVPCへのデータegressには$0.006/GBのデータ処理料金がかかる(商用リージョン)
  • Web SearchやBedrock Managed Knowledge Baseの利用は別途課金
  • カスタムのレート制限自体には追加料金はかからない

ハンズオン手順

1. Lambda TargetをGatewayに登録し、Strands Agentsから呼び出す

代表的なケース: 都市名を受け取って固定の天気情報を返すだけのシンプルなLambda関数を、 エージェントから呼び出せるツールとして公開する。

  1. 入力(都市名)を受け取り、天気情報(ダミーでよい)を返すLambda関数を作成する。
  2. agentcore create でGatewayを作成する(対話式でCognitoユーザープール等が 自動セットアップされる)。
  3. ツールスキーマを記述した tools.json を用意し、Lambda TargetをGatewayに 登録して agentcore deploy する。
  4. Strands Agentsのエージェントコードからアクセストークンを取得してGatewayのMCP エンドポイントに接続し、ListTools でツールが登録されたことを確認する。
  5. 「東京の天気を教えて」のようなプロンプトを与え、Gateway経由でLambda関数が呼び出され、 結果が回答に反映されることを確認する。
  6. 確認後、GatewayとLambda関数を削除する。
agentcore add gateway-target \
  --name WeatherTarget \
  --type lambda-function-arn \
  --lambda-arn arn:aws:lambda:us-east-1:123456789012:function:GetWeather \
  --tool-schema-file tools.json \
  --gateway MyGateway

agentcore deploy

2. Cognitoによるインバウンド認証(JWT)を設定し、一連の流れを試す

代表的なケース: 認可されたユーザー/エージェントだけがGatewayを呼び出せるようにする。

  1. Cognitoユーザープールにテストユーザーを1件作成し、パスワードを設定する。
  2. Gatewayのインバウンド認証(CUSTOM_JWT)で、CognitoのOIDC Discovery URL・ 許可するAudience/Client ID/Scopeを設定する。
  3. aws cognito-idp admin-initiate-auth でテストユーザーとしてサインインし、 IDトークン/アクセストークンを取得する。
  4. 取得したトークンを Authorization: Bearer ヘッダーに付与してGatewayの MCPエンドポイントにリクエストし、ツール一覧が取得できることを確認する。
  5. トークンなし、または不正なトークンで同じリクエストを送り、401/403で拒否されることを 確認する。
  6. 確認後、テストユーザーとGatewayを削除する。

3. セマンティックツール検索を有効化し、複数ツール登録時の挙動を確認する

代表的なケース: ツール数が数十個規模に増えたときに、エージェントが自然言語クエリで 目的のツールを見つけられるかを検証する。

  1. 説明文を変えたLambda Targetを10個以上Gatewayに登録する(注文照会・注文キャンセル・ 在庫確認・配送状況確認など)。
  2. Gatewayの Semantic search of tools オプションを有効化する。
  3. x_amz_bedrock_agentcore_search に「注文をキャンセルしたい」のような 自然言語クエリを投げ、関連度の高いツールが上位に返ることを確認する。
  4. セマンティック検索を無効にした状態と比較し、プロンプトサイズや応答速度の違いを 観察する。
  5. 確認後、追加したTargetとGatewayを削除する。

理解度クイズ

Q1. AgentCore Gateway の役割として正しいものはどれか?

AgentCore Gateway は、既存のAPI・Lambda・他のエージェント(A2A通信)・複数モデルプロバイダーへのルーティングまでを扱う、エージェント向けAIゲートウェイ。エージェントが単一のMCPエンドポイントを呼び出すだけで、背後の各Targetにアクセスできるようにする。

Q2. インバウンド認証とアウトバウンド認証の違いとして正しいものはどれか?

インバウンド認証はGatewayを呼び出すエージェント/クライアントを検証する仕組み(JWTベースのCUSTOM_JWTが中心)。アウトバウンド認証はGatewayが各Targetの裏側(Lambda実行ロール、APIキー、OAuthなど)へアクセスする際の認証情報で、Targetごとに異なる方式を設定できる。

Q3. セマンティックツール検索(x_amz_bedrock_agentcore_search)の目的として正しいものはどれか?

Targetの数が増えるとすべてのツール定義をプロンプトに含めるのは非効率になる。セマンティックツール検索は自然言語クエリから関連度の高いツールを絞り込んで返すことで、プロンプトサイズとレイテンシを削減する。
